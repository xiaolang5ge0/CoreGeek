# 自进化任务系统逻辑

## 一、任务概览

- **任务点**：2 个（自进化类），分别位于地图两侧阵营区域
- **完成冷却**：30 回合，完成后约 50 分 + 30 金/次
- **执行角色**：开拓者（pioneer），唯一能接任务的角色
- **任务预算**：每个任务 `timeout_rounds` 回合（通常 10-15 回合），超时平台强制终止
- **提交策略**：部分答案可多次提交，平台按历史最高通过率结算 → **边做边提交**
- **结束条件**：完成 / 超时 / 开拓者离开任务点 1 格 / 开拓者死亡 / 夜间遇敌放弃

## 二、核心异步机制

所有交互均有 **1 回合延迟**，形成异步事件驱动：

| 发出 | 下回合收到 | 说明 |
|------|-----------|------|
| `acceptTask` | `phaseTask` 出现 | 任务确认 |
| `prompt`（LLM 提问） | `llmResp` | LLM 响应 |
| `executeCmd`（沙盒命令） | `lastCmdResult` | 命令执行结果 |
| `submitAnswer` | `errors`（errorCode=2 答案错误） | 提交反馈 |

> **关键约束**：任务执行期 LLM 不限次且不占每日 3 次额度。

## 三、FSM 状态机

```
IDLE → MOVING → WAIT_ACCEPT → WAIT_LOCATE

                                    ├→ WAIT_CMD ──────────────────→ ↑
                                    ├→ _ws_action(工程修复) → WAIT_CMD
                                    └→ WAIT_LLM ←──────────────────┘

DONE → IDLE（reset，可接新任务）
```

## 四、各状态详细逻辑

### 4.1 IDLE — 空闲

**入口**：初始状态 / 任务完成 / 任务放弃后 reset

**每回合行为**：
1. 遍历 `snap.our_tasks`，筛选 `is_valid=True` 且 `cold_down_rounds==0` 的任务点
2. 对照 `snap.task_points` 确认任务点位置
3. 选最近的候选任务点
4. **时间预算检查**：
   - `rounds_to_task`：BFS 距离估算走到任务点需多少回合
   - `est_task`：任务本身耗时（最多 8 回合）
   - `rounds_home`：从任务点回基地的回合
   - 必须 `rounds_left > rounds_to_task + rounds_home + margin + est_task`
5. 预算足够 → 出发（MOVING）；不够 → 回基地附近待命

**夜间特殊处理**：
- 夜间有威胁（机器人）→ 放弃任务，回防
- 夜间无威胁且配置允许 → 可继续做任务（以天亮前为截止）

### 4.2 MOVING — 前往任务点

**每回合行为**：
1. 校验目标任务点是否仍有效（`is_valid` + `cold_down_rounds==0`），失效则 reset
2. 切比雪夫距离 ≤ 1 → 到达，发 `acceptTask`，跳转 WAIT_ACCEPT
3. 未到达 → BFS 走向下一步

### 4.3 WAIT_ACCEPT — 等待任务确认

**每回合行为**：
1. `snap.phase_task` 非空 → 任务确认，记录任务描述、超时回合、初始化迭代计数 → WAIT_LOCATE
2. 上回合 `acceptTask` FAIL（`last_action_results[pioneer.id] == False`）→ 立即 reset，不重试
3. 无 FAIL 但 phaseTask 未出现 → 重试最多 1 次（可能延迟）

**关键修复（09211645）**：
- `acceptTask` FAIL 被平台计为 errorCode 4（指令错误），5 次异常封号
- 修复：FAIL 后立即 reset，不再重试

### 4.4 WAIT_LOCATE — 等待定位命令结果

**每回合行为**：
1. 发出定位命令（首次）：
   ```bash
   f=$( [ -f "task_*.md" ] && echo "..." || find /tmp/selfEvolutionTask ... -name "*.md" );
   d=$(dirname "$f"); echo "__FILE:$f"; echo "__DIR:$d";
   for x in "$d"/*.md; do echo "__DOC:$x"; cat "$x"; done; echo "__END"
   ```
2. 等待 `lastCmdResult` 到达
3. 结果到达后缓存 `cached_task_desc`，按任务类型分流：
   - **API 类**（文档含 `localhost:` / `http://`）→ WAIT_HARVEST，发收割命令
   - **工程修复类**（含 `ws_N/` + `./check`）→ `_ws_action()` 自发修复
   - **其他** → WAIT_LLM

**防卡死机制**：连续 3 回合无结果 → LLM 接手找文件

### 4.5 WAIT_HARVEST — API 收割

**每回合行为**：
1. 发出收割命令（首次）：内嵌 Python 脚本（base64 编码），自动探测：
   - 认证方式（Bearer / X-API-Key / token / param / none）
   - 城市参数名（city / location / cityName ...）
   - 城市名（从答案模板 → 标题 → 词频）
   - 分页参数（page 风格 / offset 风格）
2. 全量分页采集（offset 递增，最多 50 页）
3. 输出 `__API` 事实行 + `__ANSWER` JSON（如果所有字段齐备）
4. 结果到达：
   - 有 `__ANSWER` → 直接提交（省 2 回合 LLM 往返）
   - 只有 `__API` 事实 → LLM 根据事实组装答案

**答案一致性校验**：
- `total_count` 与实测不符 → 拒绝，要求用实测值
- 实测 0 条 → 禁止提交空答案

### 4.6 WAIT_LLM — 等待 LLM 响应

**每回合行为**：
1. 发出 prompt（首次或 LLM 要求继续）
2. 等待 `llmResp` 到达
3. 解析 LLM 输出：
   - `CMD: <命令>` → 跳转 WAIT_CMD，发 executeCmd
   - `ANSWER: <答案>` → 校验后提交
   - 无法解析 → 重发 prompt

**振荡检测**：
- `llm_loop_rounds` 记录 WAIT_LLM ↔ WAIT_CMD 循环次数
- 超过 `task_llm_stall_rounds`（默认 4）→ 提交保底答案或结束
- 软失败（`[FAIL]`）不重置振荡计数

**LLM 响应为空处理**：
- deadline 临近且有最佳答案 → 先提交保底
- 连续 3 回合无响应 → 重发 prompt 防卡死

### 4.7 WAIT_CMD — 等待命令执行结果

**每回合行为**：
1. 等待 `lastCmdResult` 到达
2. 结果到达后：
   - **提取 TOKEN**：`./check` 成功输出 `TOKEN: xxx` → 直接提交 `{"token": "xxx"}`
   - **提取 JSON 答案**：API 类任务返回的完整 JSON → 缓存为 `best_answer`
   - **工程修复类**：若非 `./check` 命令，自动追加 `./check` 验证
   - **_ws_action 确定性修复**：工程修复类任务，从 spec.md 或 `[FAIL]` 输出解析修复指令
3. 命令失败（exitCode ≠ 0）：
   - 记录失败次数，连续 4 次 → 任务结束
   - 失败输出喂给 LLM，让 LLM 换方案
4. 软失败（exitCode=0 但 `[FAIL]`）：
   - `soft_fail_streak += 1`，连续 3 次 → 提交保底或结束
   - **不重置** `llm_loop_rounds`（关键：防止振荡永不触发降级）
5. 命令真正成功 → 重置振荡计数和软失败计数
6. deadline 前最后 1 回合且有最佳答案 → 直接提交
7. 累积证据到 `evidence_buffer`（30000 字符）
8. 回到 WAIT_LLM

### 4.8 WAIT_SUBMIT — 等待提交反馈

**每回合行为**：
1. `phase_task` 清空 → 任务结束
2. `errorCode=2` → 答案错误，加入对话历史，LLM 改进后重提
3. `errorCode=1` → 超时，任务结束
4. 无错误且任务仍在 → 部分正确，等待结算

## 五、工程修复类任务（_ws_action）

**识别条件**：题面含 `ws_N/` 和 `./check`

**两阶段执行**（各一次性，零 LLM 额度）：

### 阶段 A：探测
```bash
cd {ws_path} && find . -maxdepth 2 | head -40; cat spec.md; sed -i 's/\r$//' check; chmod +x check; ./check
```
- 读取目录结构 + spec.md + 首次 check 结果
- 结果进入 `cached_task_desc` + `last_cmd_result`

### 阶段 B：修复
从 spec.md 文本解析确定性修复指令（`_spec_fixes`）：
1. **文件/目录必须存在**（权限 xxx）→ `mkdir -p` + `chmod`
2. **配置文件第 N 行：`值`** → `sed Ns` 原地替换

如果 `_spec_fixes` 认不出，从 `[FAIL]` 输出兜底解析（`_check_fail_fixes`）：
- `[FAIL] DIR path — 期望 exists,755` → `mkdir -p + chmod`
- `[FAIL] LINE file:N — 期望 X 实际 Y` → `sed Ns` 替换

修复命令格式：
```bash
cd {ws_path} && S(){ ... }; mkdir -p ...; S "config.conf" 3 "port 9090"; ./check
```

最多 2 次修复尝试（`ws_fix_count <= 2`），之后交给 LLM。

## 六、每回合交互时序

以一次完整的工程修复任务为例：

```
回合 N:   IDLE → 找到任务点 → MOVING → move 走向任务点
回合 N+1: MOVING → move（继续走）
回合 N+2: MOVING → dist≤1 → acceptTask → WAIT_ACCEPT
回合 N+3: WAIT_ACCEPT → phaseTask 出现 → 发定位命令（executeCmd）→ WAIT_LOCATE
回合 N+4: WAIT_LOCATE → lastCmdResult 到达（__FILE/__DIR/__DOC）→
           识别为工程修复类 → _ws_action 探测命令 → WAIT_CMD
回合 N+5: WAIT_CMD → lastCmdResult 到达（find + spec.md + check 首次输出）→
           _ws_action 修复命令（spec_fixes 解析）→ WAIT_CMD
回合 N+6: WAIT_CMD → lastCmdResult 到达（修复后 check 输出 TOKEN）→
           提取 TOKEN → submitAnswer → WAIT_SUBMIT
回合 N+7: WAIT_SUBMIT → phaseTask 清空或无错误 → 任务完成 → DONE → IDLE
```

**总计约 7 回合**（定位 2 + 探测 1 + 修复 1 + 提交 1 + 确认 1 + 走路 N 回合）。

API 类任务类似，但用 HARVEST_PY 替代 _ws_action：

```
回合 N:   IDLE → MOVING → ... → acceptTask → WAIT_ACCEPT
回合 N+3: WAIT_ACCEPT → phaseTask → 定位命令 → WAIT_LOCATE
回合 N+4: WAIT_LOCATE → 定位结果 → 识别 API 类 → HARVEST_PY → WAIT_HARVEST
回合 N+5: WAIT_HARVEST → 收割结果（__API + __ANSWER）→ 直接提交 → WAIT_SUBMIT
回合 N+6: WAIT_SUBMIT → 完成
```

**总计约 6 回合**（比工程修复快 1 回合）。

## 七、Prompt 构造

`_build_prompt(snap)` 构造自包含的 LLM prompt，包含：

| 段落 | 内容 |
|------|------|
| 时间预算 | 剩余/总回合数 |
| 第一轮提示 | 必须一条命令完成信息收集（仅首轮） |
| 任务描述 | phaseTask 原文 |
| 已读取的任务说明 | cached_task_desc 缓存（截断 2000 字符） |
| 上回合命令输出 | last_cmd_result（截断 3000 字符） |
| 累计沙盒证据 | evidence_buffer（30000 字符） |
| API 实测事实 | harvest_facts 强约束（认证头/参数/城市/total_count） |
| 跨任务 API 经验 | persisted_api_facts（认证头/参数名跨任务复用） |
| 历史交互 | conversation 摘要（最近 N 条） |
| SOP 经验 | sop_by_type 按任务类型注入 |
| 命令规范 | 单行/300 字符限制/JSON 处理 |
| API 类任务提示 | 认证方式试错策略 |
| 通用流程 | 8 条规则（禁止 cat、先 ./check 再修复、禁止盲抄） |
| check 精确匹配规则 | 禁止尾分号/多余空格/引号包裹 |
| 失败警告 | 连续命令失败/软失败的强警告 |
| 紧急提示 | deadline 临近时强制给答案 |

**LLM 输出格式**：严格一行，`CMD: <命令>` 或 `ANSWER: <答案>`。

## 八、关键防御机制

| 机制 | 触发条件 | 处理方式 |
|------|---------|---------|
| acceptTask FAIL 不重试 | 上回合 acceptTask FAIL | 立即 reset，找其他任务点 |
| 任务点失效检测 | 移动过程中任务点 isValid=false 或冷却中 | 放弃，回 IDLE |
| 振荡超时降级 | WAIT_LLM↔WAIT_CMD 循环 ≥ 4 轮 | 提交保底答案或结束 |
| 软失败计数 | ./check 输出 [FAIL]（exitCode=0） | 不重置振荡计数，连续 3 次降级 |
| 命令失败计数 | exitCode ≠ 0 | 连续 4 次 → 任务结束 |
| prompt 丢弃检测 | 连续 3 回合无 llmResp/lastCmdResult | 重发 prompt |
| 冗余 cat 检测 | LLM 输出 cat spec.md/task_*.md（已在 prompt 中） | 跳过，重发 prompt 要求直接修复 |
| 重复 check 检测 | 软失败后 LLM 只输出 ./check 无修复 | 拒绝，强制输出 sed/mkdir |
| 放弃性答案检测 | LLM 返回 {"status": "pending_token"} | 拒绝，要求重新尝试 |
| 答案一致性校验 | total_count 与收割实测不符 | 拒绝，要求用实测值 |
| 时间预算 | 出发前检查走路+任务+回来是否赶在黄昏前 | 不够则不出发 |
| 黄昏回防 | 来不及完成任务 | 先提交最佳答案再撤离 |
| 夜间遇敌 | 夜间有机器人威胁 | 放弃任务，回防 |
| 提交前重算 | API 类任务提交前 | 从 harvest_facts 重算 types/total_count |

## 九、跨任务经验复用

### persisted_api_facts
- 记录已确认的 API 认证头（Bearer/X-API-Key）和城市参数名
- 后续 API 任务零试错直接复用

### sop_by_type
- 按任务类型分类的 SOP 经验
- `engineering`: "先 ./check 拿 FAIL 再 sed 修复..."
- `api`: "Bearer + location 参数..."

### evidence_buffer
- 累积沙盒命令输出（30000 字符）
- 提供完整证据链，避免 LLM 丢失早期探测结果

## 十、提交前答案修正（_recompute_answer_fields）

API 类任务提交前从实测数据重算：

1. **total_count**：用 `harvest_facts["total_count"]` 覆盖
2. **types**：从 `__API_DIST type(N) {...}` 行重算，字典序排序，去除无效类型
3. **world_heritage_count**：从 `__API_DIST` 行重算含"世界/遗产"的计数
4. **错字修正**：`国家历史文化明城` → `国家历史文化名城` 等

## 十一、HARVEST_PY 脚本

内嵌在 `task_agent.py` 中的 Python 脚本（base64 编码传输），负责：

1. **定位任务目录**：`TASK_DIR` 环境变量或递归搜索
2. **读取文档**：提取 base URL / 路径 / 密钥 / 城市
3. **参数探测**：遍历 `paths × auths × city_variants × city_params`，找记录数最多的组合
4. **分页全取**：offset 递增（最多 50 页），id + JSON hash 双重去重
5. **输出**：
   - `__API status=OK base=.. path=.. auth=.. city_param=.. pager=.. city=.. unique=N total=T`
   - `__API_KEYS [...]`
   - `__API_DIST field(N) {...}`
   - `__ANSWER {...}`（所有字段齐备时）

## 十二、配置参数

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
