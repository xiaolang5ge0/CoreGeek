## 一、计分红利重估（先看钱在哪）

任务书第六章：

| 来源        | 公式                                             | 量级                                       |
| --------- | ---------------------------------------------- | ---------------------------------------- |
| score1 任务 | 奖励(实测 120) + 5×标准回合数/(完成回合−接取回合)；部分完成 = 奖励×通过率 | **单 120，速通 bonus 最多 +25~50，部分分 120×通过率** |
| score2 击杀 | 小1/中2/大4/BOSS10                                | 每夜几十只 ≈ 20-50/夜                          |
| score3 生存 | Σ 10×day×存活系数（基地未毁=1，被毁当天及之后=0）                | **10 天满 550；day1 死只剩 10**                |

关键换算：

- **任务点是全场最大杠杆**：任务书 5.3「再次接取需等待 30 个回合刷新」，2 个任务点 × 白天 70 回合  
  ≈ 每天可接 4 单 ≈ **480-600 分/天**。我们当前每天只做 1-2 单（120-240），**这是 200-300 分与  
  691 分的主要差距来源**（比击杀分更稳定、更可控）。
- 生存分是**递增**的（day10 单天 100）：早死一天损失的是后面所有天的累加。day1 被推平 ≈ 只拿 10 分。
- 速通 bonus 量级不大（5×timeout/耗时，耗时 5 回合仅 +10~15），**"做出来"远比"做得快"重要**；  
  但**部分分（通过率）很值钱**——答对 2/3 字段 = 80 分，不该空手而归。

## 二、角色策略与分工：值得优化的点

### A 级（高杠杆 / 建议本轮做）

**A1. 夜间 `must_return` 恒真，夜间任务流被跳过**

- `fsm_pioneer._day_cmd` L109：`must_return = turn.rounds_until_night <= travel + margin`；  
  夜间 `rounds_until_night` 恒为 0 → must_return 恒真 → pioneer 不在 CP 就先归位，  
  `_task_flow` 被整段跳过；与 brain L837「兵潮已清距天亮>30 就出行动」的意图直接冲突。
- 修：夜间改用 `rounds_until_dawn` 判据（或直接跳过 must_return 分支）。

**A2. 小车完全没用起来（任务书 4.6.4 红利漏接）**

- 任务点 2 完成**奖励小车**：白天可用、驾驶后**移动 2 格/回合**、车上可采矿/建造/交易/做任务、  
  一人一车、夜晚第一回合消失。
- 当前只有 `fsm_pioneer._vehicle_rank`（P2-11，优先选任务点 2），**没有任何驶入/驾驶/利用逻辑**  
  （protocol 已有 `is_driving`、`vehicle_cells` 支持，但无人消费）。
- 价值：pioneer 往返任务点↔基地↔商店效率≈翻倍 → 直接提升 A 级任务吞吐；工人驾驶也能加快采石建墙。
- 修：完成任务点 2 后，pioneer 路线规划把小车格当作"顺路必经"；规划步长按 2 格/回合估算时间预算。

**A3. day1 墙环闭环不住（推平事故的帮凶）**

- `brain.py` L520 `day1_helper` **定义后从未使用**（死代码）→ "Day1 双工人帮建墙"实际失效；  
  派单处只剩"挖矿工仅在 day1 石头>20 且墙<14 时帮建"——石矿每座仅 10 次，>20 门槛 day1 早期几乎达不到。
- 结果：day1 只建成 13/14，第 14 面（实战为 (9,21)）缺口过夜（U26 待验证）。
- 修：用 `capacity = (rounds_until_night - buffer)/WALL_ROUNDS_PER` 判"单人是否建得完"，  
  建不完就派第二人帮建（不必等 stone>20）；或至少把门槛降到 stone≥10。

### B 级（明确收益 / 建议做）

**B1. 升级优先级与任务书数值不匹配：武器升级被墙压住**

- 现状：`upgrade.py` 正面墙 L3=1、拐角=2、侧面 L1=5 > **武器 L2=10、武器 L3=20**、墙 L1→L2=15、墙 L2→L3=25。
- 任务书数值：火箭 L1 单弹头/射程10/冷却3 → **L2 双弹头/射程15 → L3 三弹头/全图**；  
  加特林 L1 25×1/射程3 → L3 25×3/射程7；墙 L1 1000 → L3 2000。
- 判断：墙再厚也会被啃穿（大机器人 20 攻，10 只 = 200/回合，L3 墙 2000 血也就 10 回合）；  
  **火力才是清潮与击杀分的根本**，且火箭 L3 全图是质变（不用出门就能打）。
- 修：武器 L2/L3 提到 5/8（高于墙 L3 的 12/15），正面墙 L3 降到 12、拐角 15。

**B2. 循环依赖把火力锁死在威胁模式**

- 正面墙未达 L3 → 券备货 priority −1（死线）永远压过 WallFixer(0) → `fire._defense_safe`  
  要求工人持 WallFixer≥8 恒不满足 → **积分模式永远不可达**（IKKIA9-Q1 的场景会重演）。
- 修：券备货死线优先级让位 WallFixer 备货；或 `_defense_safe` 降级为"墙无濒危 + 有 fixer≥3"。

**B3. 夜间开火窗口被"移动"吃掉**

- brain L908 只在 pioneer 本回合无指令时开火，而 pioneer 几乎每回合都在移动（代码注释已承认）。
- 夜间 `_night_control_goal` 每回合重算，若安全格抖动 → 来回走 → 零开火。
- 修：pioneer 到达"可开火的控制格"后粘住（sticky），只有危险/无目标/武器全毁才重新选格；  
  并让 goal 选择结果在若干回合内保持稳定。

**B4. day1/day2 夜修理工仍外出采矿**

- `fsm_worker` L257：仅 **D3+** 夜无条件就位 repair_post；D1-D2 夜仍可外出采矿（L258）。
- day1 夜恰是防线最薄的时候（墙 L1、可能还缺 1 面），而夜里矿点还有机器人威胁。
- 修：D1/D2 夜一律就位；或"墙未闭环 / 有墙 <50% 血 / 有机器人在基地 6 格内"时就位。

### C 级（红利 / 可选）

- **C1 同回合并行下发**：接口 Response 的 `prompt` 与 `executeCmd` 是两个独立字段，  
  **可以同回合既问 LLM 又跑沙盒命令**。当前串行（发 cmd → 等结果 → 发 prompt，2 回合/交换）。  
  改成并行可让 timeout 内的交互次数**翻倍**（见第三节 T2）。
- **C2 任务期 LLM 不限额度**：接口文档明确「自进化任务执行期间不受每日 3 次限制，也不计入额度」。  
  需确认代码没有把 `LLM_DAILY_LIMIT=3` 误用到任务期提问上。
- **C3 基地升级当急救**：基地 L1 1500 → L2 3000（且升级回满血），当前 priority 45 太低。  
  基地开始掉血时把 StationUpgradeVoucher 提到最高（100 金换 1500 血 + 回满）。
- **C4 矿锁**：`fsm_worker` L388-397 仅 repairer 会因 prefer 变化释放矿锁，miner 锁死后不随行情切换。
- **C5 金币资源竞争**：`upgrade.plan` 的 budget 是本地顺序扣减，与 pioneer `_buy_qty`（按 gold//cost 全额）  
  无全局预留 → 同回合两人下单常有一人被 `gold_not_enough` 拒，整回合作废。加全局预留。
- **C6 抓捕红利**：抓敌方 imp = 20 金 + 消灭对方破坏能力；任务书「捣乱鬼执行破坏时位置全图可见」→  
  可做成"敌 imp 一出现就派最近工人去抓"的主动防御（当前是机会性 catch）。
- **C7 岗位固化风险**：`role` 只在 `_day` L528 赋值（worker[0]=repairer / worker[1]=miner），  
  夜里若工人阵亡次日复活产生新 ID，FSM 默认 ROLE_MINER → 可能出现"两个矿工、零修理工"。  
  修：岗位按存活集合重算（至少保证一名 repairer）。

## 三、自进化任务：失败原因与加固方案

### 3.1 任务书约束（先对齐事实）

- 5.3：开拓者在**任务点主动领取**；与沙盒交互；最终提交答案。
- 任务结束条件（4 选 1）：完成 / 超时 / **离开己方任务点周围一格** / 开拓者死亡。  
  结束后无论是否完成，**都按通过率给分** → 部分分必须拿到。
- 刷新：**再次接取需等待 30 回合**。
- 接口：`executeCmd` 仅任务期间可用，执行超时 15 秒（沙盒故障/超时**不计异常**）；  
  `lastCmdResult` 格式 `[exitCode:N]\n<输出>`，超 64KB 追加 `[TRUNCATED]`。
- 错误码：2=答案错误（不完全正确也算）；5=LLM 额度超限（**任务期豁免**）。

### 3.2 失败原因归类（三场实证）

| 类型                             | 证据                                                                                                                                         | 根因                                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 上下文丢失 → 复读死循环**（IKKJ2K，主因） | r11 接取、r12 探索、r13-23 共 7 次 prompt，**LLM 反复回同一脚本**（r19 只 `head -5` 试探），prompt_len 从 7498 涨到 18650 后 r22/r23 完全相同；`answer` 恒空；r25 timeout 全废 | `task.py` L517 `_on_cmd_result` 只写 `COMMAND:`/`RESULT:`，**从不记录 LLM 自己的回复** —— transcript 里没有 assistant turn。LLM 每轮只看到"我跑过什么命令"，看不到"我上次得出什么结论/为什么没提交" → 原地打转 |
| **② 答案就在沙盒输出里却不会取**            | IKKJ2K r14/16/18/22 沙盒输出的裸 JSON 就是答案                                                                                                       | 只有 `FINAL_ANSWER:` 标记才自动提交（L71/L539），**没有"末次裸 JSON 兜底提交"** → 本可拿的 120×通过率 变成 0                                                                              |
| **③ force/死线只劝不兜底**            | force_answer 后拒收 cmd，却重发几乎相同的 prompt，7 次空转                                                                                                 | L792-795 拒 cmd 后直接回 `ST_LLM`；`_at_deadline` 剩 ≤2 回合才 force（太晚）；无"从 transcript 抽最后一个像答案的 JSON 提交"的降级路径                                                       |
| **④ 探测命令写死无 fallback**         | IKKJ2J r24 `_probe_cmd` 返回 `exitCode:127`、`__WS:.`（find 未命中 check，退化成列根目录），靠 LLM 多轮救回（运气）                                                  | `_explore_cmd` / `_probe_cmd` 硬编码，失败后无降级目录猜测                                                                                                                |
| **⑤ 预算与真实延迟不匹配**               | timeout=15、2 回合/交换 ≈ 5 次交换；首轮 explore 又吃掉 1 次                                                                                              | `skip_explore` 阈值 ≤10，**timeout=15 未触发**；`max_loops=max(2,(timeout-4)//2)` 未扣除已用交换                                                                          |
| **⑥ 失败不沉淀**                    | SOP/notes 仅在 `_confirm_done` 成功时写入 → 同题重做从零试错                                                                                              | `_maybe_extract_sop` L1019 只在成功路径调用                                                                                                                         |

对照组（成功样本）：IKKJ2E r12-r16 = 3 次交换收工（脚本一次跑对）；IKKJ2J r22-r31 = 硬编码探测失败后  
靠 LLM 多轮救回。**结论：成功靠运气，失败是结构性缺陷（尤其 ①②③）。**

### 3.4 一条硬约束提醒

任务书：**离开任务点周围一格 = 任务结束**。→ 接任务前必须确认"能在不离开的情况下做完"，  
且**夜间回防会直接终止在做的任务**（只拿部分分）。当前 `must_return`/回家逻辑没有把这个代价算进去：  
建议"接单前先判断是否跨夜/是否需要回防，会中断就不接"（与 A1 一起改）。
